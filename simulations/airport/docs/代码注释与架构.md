# 代码注释与架构说明

本文解释机场示例中“机器狗到位 → 无人机复核 → 运输机器人交接 → 全部返航”的联动关系，便于路演时讲解和后续接入真实设备。代码中的英文标识与 ROS topic 保持不变，中文注释文件用于快速定位职责。

## 一次任务如何联动

`portal.py` 是任务编排器。它为每个作业区建立一条依赖链：

```text
queued
  └─ inspect       机器狗沿 RMF 路线巡检并实测到达
      └─ air       对应无人机收到三维目标，达到 6/7/8 m 后拍摄复核
          └─ queue  等待两台共享运输机器人中的一台空闲
              └─ transport  运输机器人沿 RMF 路网前往作业区
                  └─ handoff 机器狗与运输机器人同时到位并驻留 4 秒
                      └─ return 地面设备返航，无人机降落
```

只有测量条件满足，编排器才会推进下一阶段：

- `near()` 比较 `/airport/agents` 中的实测位置和目标位置；
- `air_state()` 等待无人机的测量高度和 `verified` 标志；
- `wait_until()` 轮询测量条件，以墙上时间限制超时，暂停时顺延超时；交接和无人机定点驻留使用 Gazebo 仿真时钟计算；
- `handoff` 记录双方位置、驻留时间和 `simulated_work_order_acknowledgement` 类型；
- 第二次 `POST /api/mission` 在已有任务时返回 HTTP 409。

## 数据流

```text
portal.py --/task_api_requests--> RMF fleet adapter --> fleet manager
                                                           |
                              /robot_path_requests <-------+
                                       |
                                       v
portal.py --/airport/air_command--> controller.py -- /cmd_vel --> Gazebo 机器狗
                                       |         -- /target --> Gazebo 无人机
                                       |
portal.py <---- /airport/agents --------+ <--- Gazebo 里程计 / AMR robot_state
portal.py <---- task_state_update -------- RMF dispatcher / adapters (WebSocket :7878)

Gazebo 相机 -- ROS Image --> portal.py -- MJPEG /camera/*.jpg --> site/
```

地面机器人由 RMF 二维交通图调度；无人机不进入 RMF 地面图，而由 portal 根据作业区依赖协调。这样既保留 RMF 的车队/交通示范，又明确说明空中部分的仿真边界。

## 关键接口

| 接口或 topic | 用途 |
| --- | --- |
| `GET /api/status` | 返回任务阶段、8 台设备位置/速度、告警、证据和相机状态 |
| `POST /api/mission` | 启动一次任务；已有任务时返回 409 |
| `POST /api/physics` | 使用 `{"action":"pause"}` 或 `{"action":"resume"}` 控制物理时钟 |
| `/robot_path_requests` | RMF 发送给机器狗的路径请求 |
| `/airport/air_command` | portal 发送设备 ID 和 survey 指令；controller 从配置生成对应航线、高度和坐标 |
| `/airport/agents` | controller 发布的测量状态，网页只使用这一份设备真值 |
| `/sensors/overview/overview/image_raw` | 总览相机，用于网页视频和证据截图 |

## 修改入口

- 增减设备或作业区：修改 `fleet_config.py`，再运行 `build_scene.py` 生成世界和配置。
- 调整联动条件、等待时间或工单状态：修改 `portal.py` 的 `run_cell()`、`near()` 和 `handoff` 段落。
- 调整机器狗/无人机运动：修改 `plugin/motion.cpp`，然后重新 `docker compose build`。
- 调整网页标签、运行态提示和颜色：修改 `site/app.js` 与 `site/style.css`。
- 调整 RMF 节点和车队适配器：修改 `airport.launch.py`。

## 日志和排错

```powershell
docker compose -p rmf-airport logs -f simulator
docker compose -p rmf-airport exec simulator bash
```

容器内日志位于 `/var/log/airport/`：`gazebo.log`、`rmf.log`、`controller.log`、`portal.log` 和 `gui.log`。如果网页显示“等待仿真”，先查看 `gazebo.log` 和 `rmf.log`；如果设备在线但不动，检查 `controller.log` 中的 `/robot_path_requests` 与 `/airport/air_command`。

## 仿真边界

官方 Open-RMF Airport Terminal 仅作为三维建筑上下文，不代表真实机场测绘。机器狗、无人机、告警、相机证据和工单交接均为可重复的仿真逻辑；接入实体设备时，需要把 `plugin/motion.cpp`/`controller.py` 替换为设备 SDK、PX4/MAVLink 或 ROS 2 驱动，并重新做安全验证。
